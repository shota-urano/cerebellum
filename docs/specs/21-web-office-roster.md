# 21. 「オフィス」画面の社員名簿（プロフィールと手動起動社員）

**親**: [`00-overview.md`](./00-overview.md) ｜ **担当**: Frontend ｜ **範囲**: `features/office/`（社員カードシート・部署ルームのブロック分け・カード内ミニライン・`?line=` 絞り込み）

[`20-web-office.md`](./20-web-office.md)（confirmed・実装済み）への**増分**。20 の情報設計（部屋＝役割・正常なものほど静かに・読むだけ）は変更せず、席から「この社員は何者か」を読める面を足す。

## 1. 目的

勤務帯と直近報告は出たが、**社員の職務内容が画面のどこにも無い**。19本の automation は名前（`x-pdca`・`night-blindspot`）から仕事が推測できず、「何をする人か」「自分はどう呼ぶのか」「出てきた成果の何を確かめるべきか」が人間の記憶にしか無い。増員が続けば忘れる（2026-08-27 ユーザー起点・Linear USL-309「社員名簿の作成」）。

同時に、**勤務帯を持たない社員**（`/ask`・`/idea-forge` のように人間が打って動く skill）が増える前提がある。20 は「勤務開始時刻の昇順に並ぶ社員」だけを想定しているので、勤務帯 `null` の社員は席に「勤務時間未設定」と出て**設定漏れに見える**。役割は同じ部屋のまま、起動方式だけを区別して見せる必要がある。

手書きの名簿ファイルは作らない。20 §1 と同じ理由——`80_運用ガイド/` の手書きHTML2枚が現状と合わなくなった前例があるので、**名簿の正本は各 skill の `SKILL.md` frontmatter に置き、`office.json` 経由で機械的に運ぶ**（→ §9）。

**2026-08-27 の追補**（第1版を本番へ入れた直後のユーザー指摘「使ってるエージェントがわからんし、どこを確認したらいいかもわからない」から）。第1版に足りていなかったのは3つ:

1. **担当エージェント**（§3.2）。第1版は `skill`（何の手順で動くか）しか出しておらず、**誰が動かすか**（Claude Code / Codex・どのモデル）が画面に無かった
2. **確認する場所**（§3.6-5）。`checks[]` は「何を見るか」しか持たず、**どこを開けば見られるか**が無いので結局 Vault を手で探すことになる
3. **前後の流れ**（§3.6・§3.7）。1人の名簿だけでは「自分が止めると誰が空回りするか」が読めない。人間の仕事もノードとして置いた 1-hop のミニラインでこれを出す。**全体を一望させる図は作らない**（§7・20 §1 の轍）

## 2. 入出力

- **入力**: `GET office.json`（20 §2 と同一。接続規則も同一）
- **出力**: なし（表示のみ。20 §7 を踏襲——起動・停止・編集・即時実行は持たない）
- **経路**: `/office?room={id}&employee={automation_id}`（社員カード）／`/office?line={id}`（ライン絞り込み・§3.7）／既存の `room`・`desk`・`run` は不変

cerebellum のサーバーは経由しない（Rust・SQLite・API・スキーマの変更ゼロ）。20 と同じく Frontend だけで完結する。

`office.json` の `employees[]` に次が増える前提で書く（形の正本は second-brain の `build_office.py`。**cerebellum 側は受け取って描くだけ** → §9 に提案とその理由。`trigger`・`profile.job`・`command`・`checks`・`doc` は第1版で実装済み、`agent`・`line`・`upstream`・`downstream` が追補分）:

```
employees: [ { automation_id, name, skill, enabled, shift, next_run_at, last_run_at, last_run_id,
               trigger,                              // "scheduled" | "manual"（社員の起動方式）
               profile: {                            // 名簿の本文。無い社員もいる（null 可）
                 job: string,                        // できる仕事内容・1行
                 command: string | null,             // 人間が打つコマンド（例 "/x-post"）。無ければ null
                 agent: string | null,               // 担当エージェント（例 "claude-code (opus)" / "codex"）
                 checks: string[],                   // 実行後に人間が確認すべきこと
                 line: string,                       // 所属ライン（下の値域）。独立は "none"
                 upstream: string[],                 // 直前のノード（1-hop）
                 downstream: string[],               // 直後のノード（1-hop）
                 doc: string | null } } ]            // 名簿の正本の在処（例 ".claude/skills/x-post/SKILL.md"）
```

- **`line` の値域**: `knowledge` | `x` | `harness` | `learning` | `note` | `incubate` | `dev` | `rakuten` | `none`（配属の実データは §11）
- **`upstream` / `downstream` のノードは5種**。前3種は 2026-08-27 の second-brain 側回答どおりで、`place:` は本仕様で追加した（理由は §9-4）。`dest:` は 2026-09-03 追加（理由は §9-5）:

| 値の形 | 意味 | 例 |
|---|---|---|
| `<automation_id>` | 社員 | `a-collect` |
| `manual:/<command>` | 手動起動の skill（automation 未登録も含む） | `manual:/ask` |
| `human:<何をするか>` | **人間の仕事** | `human:Inbox選別` |
| `place:<どこ>` | **人間が開いて確認する場所** | `place:cerebellum（昇格するか choose）` |
| `dest:<どこ>` | **成果物の行き先**（人間は開かない） | `dest:10_Sources` |

  人間をノードにするのが要点。「あなたが Inbox を放置すると下流3名が空回りする」がこれで画面に出る（2026-08-27 ユーザー起点）。

- **利用 skill は既存の `employee.skill` を使う**。`profile` に重ねない（同じ値を2箇所で定義しない → `AGENTS.md` ルール6 と同じ姿勢）
- **`skill` と `agent` は別物**。`skill` は「何の手順で動くか」、`agent` は「誰が動かすか」。同じ skill を Claude Code で回すか Codex で回すかは automation の起動コマンドが決めるので、`skill` からは分からない（→ §9-3）
- **勤務帯 or 手動の区別は `employee.trigger` を唯一の根拠にする**。`shift` の有無から推測して「手動」と断定しない（→ §3.3-1）。**`profile.trigger` には置かない**（2026-08-27 の回答スキーマとの差分。理由は §9-1。実装済みの形もこちら）
- `runs[].trigger`（20 §2）とは**意味が違う**。run 側は「その回がスケジュール実行か手で回したか」、employee 側は「その社員の起動方式」。同一視しない（§9 でこの名前衝突に触れる）
- `profile` を持たない社員は必ず出る（素のシェル実行ジョブ・frontmatter 未整備の skill）。欠落は欠落として出す（→ §3.2-3）

## 3. 処理詳細

### 3.1 社員カードシート（`/office?employee=`）

1. **部署内の席タップは社員カードへ遷移する**（`/office?room={id}&employee={automation_id}`）。報告シートと同じフロア下端のモーダルシートで開く
2. カードは上から **名前 → できる仕事（`profile.job`）→ 勤務帯 or 手動・起動コマンド・担当エージェント・利用 skill → ミニライン（§3.6）→ 実行後に確認すべきこと → 直近状態と `headline`** の順に置く。「何をする人か → いつ動くか・どう呼ぶか・誰が動くか → どの流れの中に居るか → 出たら何を見るか」の読み順に合わせる
3. 直近 run がある社員のカード下端に「報告を見る」を置き、`/office?room={id}&employee={automation_id}&run={run_id}` へ遷移する（報告シートは 20 §3.5 のまま。全文展開もそこ）
4. `run` と `employee` が同時に指定されたときは**報告シートだけを1枚出す**（シートは常に1枚）。その閉じる先・ブラウザバック先は社員カード（`employee` を残した URL）にする。`employee` が無い既存の deep link（`?run=` 単独・MY DESK 経由）の戻り先は 20 §3.5-4 のまま変えない
5. 「閉じる」またはブラウザバックで同じ部署ルームへ戻る
6. 停止中社員（`enabled:false`）の席もタップして社員カードを開ける。名簿は在籍状態と独立に読めるべきなので、`profile` は同じく出し、状態だけ「停止中」にする

（採用しなかった案: 席タップは報告シートのままにして名簿を別導線にする——1タップ節約できるが、run を持たない社員（手動起動・未実行）の席だけタップできない／別物が開くという分岐が残る。現行実装がすでに「run がある席は Link・無い席は div」になっており、席の意味が一定でないのが認知の負債。1タップ増やして**席の意味を「社員を開く」に統一する**方を採る。報告の要旨（`headline`）はカード上で読めるので、全文まで読む回だけが2タップになる）

### 3.2 名簿項目の描画

| 名簿項目 | データ | 席 | 社員カード |
|---|---|---|---|
| できる仕事内容（1行） | `profile.job` | 出さない | 1行で出す |
| 起動方法コマンド | `profile.command` | 出さない | 等幅で出す |
| **担当エージェント** | `profile.agent` | 出さない | 等幅で出す |
| 実行後に確認すべきこと | `profile.checks[]` | 出さない | 全件を箇条で出す |
| **確認する場所** | `downstream` の `place:` ノード | 出さない | ミニライン内で強調（§3.6-5） |
| 利用 skill | `employee.skill` | 出さない | 等幅で出す |
| 勤務帯 or 手動 | `employee.trigger`・`shift.label` | 出す（§3.3-2） | 出す |
| **所属ライン・上下流** | `profile.line`・`upstream`・`downstream` | 出さない | ミニライン（§3.6） |
| **所属部署** | `profile.dept` | 出さない | 等幅で出す・タップで部署絞り込み（[26](./26-web-office-company.md) §3.1・§3.3） |
| **人間確認** | `profile.review` | 出さない | 1行で出す（[26](./26-web-office-company.md) §3.1-1） |

1. **席には名簿本文を出さない**。20 §3.1-2「正常なものほど暗く静かに」を壊さないため、席は名前・勤務帯・状態のままにする
2. `profile.checks` は**省略せず全件出す**（シートは縦スクロールする）。件数上限で切ると「確認すべきこと」が黙って消える。生成側の目安は1件80文字以内・5件以内とし、超えても画面は落とさない
3. **欠損は欠損として出す**（捏造しない・20 §2 の `skill:null` と同じ姿勢）。`profile` が無い／`job` が空 → 「名簿 未記載」＋`profile.doc` があればその在処を等幅で添える。`command` が `null` → 「起動コマンドなし」。`agent` が `null` → 「エージェント 未記載」（**起動コマンドから推測して埋めない**）。`checks` が空配列 → 「確認事項の記載なし」。`skill` が `null` → 「skill なし（素の実行）」
4. `profile.doc` は**等幅テキストとして出すだけ**でリンクにしない。Vault 配下は読み取りすら `import-routines` 経路だけ（`AGENTS.md` ルール1）で、この画面から辿らせない。名簿が古いときに人間がどこを直せばいいか分かれば足りる
5. `profile.command` に**コピーボタンを付けない**。Tailscale 内は `http://100.x.x.x` の non-secure context で `navigator.clipboard` が使えず、押しても黙って失敗するボタンになる。選択しやすい等幅表示（`user-select` を殺さない）だけにする

### 3.3 手動起動の社員（`trigger:"manual"`・`shift:null`）

1. **勤務形態の表示は `employee.trigger` だけを根拠にする**。`manual` → 「手動起動」、`scheduled` → `shift.label`。`trigger` が欠落しているときは `shift` があればそのラベル、無ければ現行文言「勤務時間未設定」を維持する（`shift:null` を「手動」と読み替えて断定しない——設定漏れと手動起動は別物で、取り違えると設定漏れが永久に見えなくなる）
2. 手動起動社員の席は勤務帯の代わりに「手動起動」を出し、`profile.command` があればそれを併記する（席で読める唯一の名簿項目。人間が「どう呼ぶか」だけは席から見えたほうが速い）
3. **部屋の分類規則（20 §3.1-3）は変更しない**。手動起動社員も skill 名で同じ4部屋へ落ちる。「手動部屋」は作らない——部屋＝役割という情報設計に対し、起動方式で部屋を切ると同じ仕事をする社員が別部屋に散る
4. 手動起動社員に**次回予定を出さない**。`next_run_at` は `null` なので、20 §3.2 の「まだ実行なし」＋`next_run_at` は「まだ実行なし」だけになる。ここに架空の予定を補わない
5. 当日 run が無いときの直近実行日の補助表示（20 §3.2 末尾）は手動起動社員にも同じく効く。週次社員が毎日「未実行」に見えるのを防ぐのと同じ理由で、手動社員も「いつ最後に呼ばれたか」で読ませる

### 3.4 部署ルームの並び（20 §3.4 の増分）

1. 部署内は **勤務帯ブロック → 手動起動ブロック → 停止中ブロック** の順に並べる。各ブロック内は `employees` の返却順のまま（勤務開始時刻の昇順。クライアントで再ソートしない）
2. 手動起動ブロックと停止中ブロックの前に区切りの小見出し（`手動起動` / `停止中`）を置く。勤務帯ブロックは先頭なので見出しを持たない（部屋名がそれを兼ねる）
3. 部署ヘッダに在籍の内訳を出す（例 `勤務帯 4名・手動 2名`）。停止中がいれば同じ行に足す
4. 部屋の奥行き計算（20 §3.4-4 の「5名以上は行数に応じて伸ばす」）には**手動起動・停止中ブロックも含めた総行数**を使う。ブロックが増えた分だけ下壁がずれて最終行が壁の外に出る事故を防ぐ

### 3.5 オフィス全景（20 §3.1 は変更しない）

1. 全景の部屋カウント `{n}名` は**在籍数のまま**（勤務帯・手動を区別しない）。全景は「昨夜の異常」と「自分の仕事」の2つだけを読む面で、勤務形態の内訳は部署内で読む（20 §3.1-2）
2. 部屋の信号（確認 / 失敗 / 処理中 / 正常）の優先順・判定に `trigger` を混ぜない。手動起動社員も run があれば同じ規則で数える。**「昨夜」の文言も変えない**——手動 run も直近 run として同じ扱いで拾う
3. MY DESK（20 §3.3）の判定は変更しない。`note = "承認待ち"` の完全一致だけが人間の仕事で、起動方式は無関係

### 3.6 ミニライン（社員カード内・パイプライン表示の主役）

**全ラインを1枚で俯瞰する専用グラフ画面は作らない**（→ §7）。代わりに、社員カードの中に**その社員の周り1-hop だけ**を出す。

1. `upstream` → **本人**（強調）→ `downstream` の3段を縦に積む。上流・下流はそれぞれ配列の順のまま並べ、**2-hop 以上先へ広げない**
2. 見出しに所属ラインを出す（`profile.line` の日本語ラベル。§3.7-2 の表）。見出しタップで `/office?line={id}` へ入る
3. ノードのラベルと導線は値の形で決まる（§2 の4種）:

| ノード | ラベル | タップ |
|---|---|---|
| `<automation_id>` | `employees` から引いた現在の `name` | その社員のカードへ（`?employee=`） |
| `manual:/<command>` | コマンドをそのまま等幅 | `profile.command` が一致する在籍社員があればそのカードへ |
| `human:<何をするか>` | 「あなた：<何をするか>」 | 無し（人間の仕事） |
| `place:<どこ>` | 等幅でそのまま | 無し（リンクにしない・§3.2-4 と同じ理由） |
| `dest:<どこ>` | 等幅でそのまま | 無し（同上） |

4. **`automation_id` が `employees` に無いときは id をそのまま等幅で出す**（改名・削除に耐える。名前を捏造しない・20 §2）。タップは無しにする
5. `downstream` の `place:` ノードには「見る場所」を併記して強調する。**これが「どこを確認するか」の答え**で、`checks`（何を見るか）と対になる。**`dest:` には併記しない**——行き先は人間が開く場所ではないので、同じピルを付けると「朝ここを開け」という嘘になる（2026-09-03。`place:00_Inbox` と `place:10_Sources` がこの誤りだった）。1枚のカードに「見る場所」は原則1つに保つ。`dest:` 側には代わりに**「行き先」を淡色（`--muted`。`--accent` は使わない）で併記**して、「開く場所」と「流れ込む先」を色で分ける（ピルの色差だけで役割が読めるようにする）
6. **`human:` ノードは他より強く出す**（人間が止まるとラインが止まるのが要点）。ただし MY DESK の承認件数（20 §3.3）とは無関係——ここは名簿の静的な流れで、`note = "承認待ち"` の実績とは別
7. 1-hop ずつカードを辿れることが、専用グラフ画面を持たない理由になっている。「上流を見る → その社員のカード → さらに上流」で流れは追える
8. `upstream`・`downstream` が空配列の側は**そのブロックを出さない**。`line` が `none`（独立）なら「独立（ラインなし）」と出す。`profile` が無い社員はミニライン全体を出さず §3.2-3 の「名簿 未記載」に畳む

### 3.7 ライン絞り込み（`/office?line={id}`）

1. 部屋（役割）とは**別軸のグルーピング**。専用画面ではなく**フロアの絞り込み**として1つだけ持つ。`line` 一致の在籍社員を、部署ルームと同じ席・同じブロック分け（§3.4）・同じ状態表示で1フロアに出す
2. ヘッダは `LINE: <日本語ラベル>` とし、内訳（§3.4-3）も同じ形で出す。ラベルは画面が持つ固定表（`line` は識別子であって可変の名簿データではないので §4 の禁止に当たらない）:

| 値 | ラベル | 値 | ラベル |
|---|---|---|---|
| `knowledge` | 知識 | `note` | note |
| `x` | X運用 | `incubate` | 着想 |
| `harness` | ハーネス | `dev` | 開発 |
| `learning` | 学習 | `rakuten` | 楽天 |
| `none` | 独立 | | |

3. **未知の `line` 値は値そのままを等幅で出す**（落とさない・20 §6 の未知 `outcome` と同じ扱い）
4. **ライン内に矢印・分岐の連結を描かない**。並びは `employees` の返却順（勤務開始時刻の昇順）のまま。流れを図にするのはカード内のミニラインだけ（§7 の境界）
5. 入口は社員カードのライン見出しだけにする。**全景（20 §3.1）にライン導線を足さない**——全景は4部屋とMY DESKだけを見せる面のままにする
6. `line` に一致する社員が居ないときは空状態（「このラインの社員は居ません」）＋全景へ戻る導線。エラーにしない
7. `room` と `line` が同時に来たときは `room` を優先する（部屋が主・ラインが従。URL を2軸で解釈しない）
8. **部署絞り込み（`/office?dept={id}`）は本節と同型**（[26](./26-web-office-company.md) §3.3）。優先順は `room`（=`dept`。[27](./27-web-office-departments.md) §3.2-1 で部屋 id が部署 id になり `?dept=` はその別名）→ `line` の2段

## 4. 設定値・確定値

- データ源・接続規則・生成の定期実行は 20 §4 と同一。cerebellum 側に**スキーマ・API を足さない**（[`02-data-model.md`](./02-data-model.md)・[`03-api.md`](./03-api.md) は無変更・Backend 作業ゼロ）

## 9. `office.json` スキーマへの意見（second-brain 側への提案）

指示された案は `employees[] .profile = { job, command, checks, trigger }`。**3点の変更を提案する**。

1. **`trigger` は `profile` の中ではなく `employee` 直下に置く**（本仕様は §2 のとおりこれを前提に書いた）。理由は2つ。(a) `trigger` は表示テキストではなく**構造属性**で、画面はこれを見て並び順（§3.4-1）とラベル（§3.3-1）を決める。`enabled`・`shift` と同じレイヤに置くのが自然。(b) `profile` は frontmatter 未整備の社員で**丸ごと欠ける**前提なので、`profile` の中に入れると「名簿を書いていない手動社員」が手動として扱えなくなる。起動方式は名簿の記載状況と独立していてほしい。
   - もし second-brain 側が `profile.trigger` を採るなら、本仕様 §2 の1行と §3.3-1 の参照先を差し替えるだけで済む。**confirmed 前に決める**（実装後に両方読む二重化はしない）
2. **`runs[].trigger` との名前衝突に注意する**。値域（`scheduled`/`manual`）まで同じで意味が違うので、片方を改名するのが安全（案: employee 側を `start_mode`、または run 側を据え置いて employee 側を `trigger` に統一する旨をコメントで明記）。改名しない場合でも、`build_office.py` と本仕様の両方に「同一視しない」を明記する（20 §2 が `name` と `title` で同じ注意書きを持っているのと同じ）
3. **`doc` を足す**（`string|null`。例 `.claude/skills/x-post/SKILL.md`）。名簿が現状と合わなくなったとき、**どのファイルを直せば画面が直るか**が画面から分かる。20 §1 の失敗（手書きHTMLが更新されないまま残る）に対する保険で、`profile` の正本が frontmatter であることを画面が自ら示す。画面は等幅で出すだけ（リンクにしない・§3.2-4）

そのまま採る点:

- `job: string`（1行）・`checks: string[]` の形。`checks` を1本の文章にせず配列で持つのは正しい（画面が箇条で出せる）
- **利用 skill を `profile` に重ねない**（既存の `employee.skill` を使う）。同じ値の二重定義を作らない
- 手書きの名簿ファイルを作らず `SKILL.md` frontmatter を正本にする方針。cerebellum 側に対応表を持たない（§4）

### 9.2 `dest:` の追加（2026-09-03・ユーザー起点）

5. **`upstream`/`downstream` に `dest:<どこ>` を5種目として足す**。`place:` が「成果物・確認する場所」を兼ねていたため、`place:10_Sources`・`place:Typefully draft` のような**行き先**に §3.6-5 の「見る場所」ピルが付き、「朝ここを開け」という嘘の指示になっていた（発端は collect のカードで「見る場所」が `00_Inbox` と `cerebellum` の2つ出ていたこと）。`place:` は人間が開く場所に限り、行き先は `dest:` へ分ける。1枚のカードに「見る場所」は原則1つ。
   - **`place:` の既存値は動く**（未知の接頭辞を落とさない §6 の姿勢と同じで、`dest:` 未対応の名簿もそのまま描ける）。second-brain 側は行き先ノードを順次 `dest:` へ移す

### 9.1 2026-08-27 の回答スキーマとの差分（追補分）

回答された案は `profile = { job, command, checks, trigger, line, upstream, downstream }`。**4点の差分がある**。

1. **`trigger` は `employee` 直下のまま**（回答では `profile` 内）。§9-1 の理由がそのまま効く——`profile` は frontmatter 未整備の社員で丸ごと欠けるので、その中に入れると「名簿を書いていない手動社員」を手動として扱えなくなる。**この形で実装済み・本番稼働中**なので、`build_office.py` 側をこれに合わせてほしい
2. **`doc` は維持する**（回答では欠落）。実装済み。名簿が古いときに直す場所を画面が自ら示すための項目で、ライン定義が増えるほど「どこを直すか」の価値が上がる
3. **`agent` を足す**（回答には無い。2026-08-27 のユーザー指摘「使ってるエージェントがわからん」への答え）。**正本は `SKILL.md` ではなく automation の起動コマンド**——同じ skill を Claude Code で回すか Codex で回すかは automation 側が決めるので、skill 側に書くと嘘になる。`build_office.py` は既に prompt から `skill` を抜いているので同じ経路で取れる。取れなければ `null`（推測で埋めない）
4. **`upstream`/`downstream` に `place:` を4種目として足す**（回答は automation_id / `human:` / `manual:` の3種）。実データの `→Typefully draft→`・`→Slack通知→`・`→25_Ideas→` は社員でも人間でもない**成果物ノード**で、3種では表せない。そして**これがユーザーの元の問い「どこを確認したらいいか」の答え**なので、別フィールド（`outputs[]`）を立てずにここへ寄せた——ラインの中間ノードと確認場所は同じものなので、二重定義を作らない（§3.6-5）
